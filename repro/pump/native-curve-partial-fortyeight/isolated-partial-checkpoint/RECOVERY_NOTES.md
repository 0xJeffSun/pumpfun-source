# Partial native/legacy Pump curve run

This isolated module reconstructs a bounded branch of `multi_hop_curve_swap`. Its baseline is the immutable Pump42 holder/nested source archive, not the changing checkout. Only `src/lib.rs` and a new `src/multi_hop_curve.rs` differ; all other 30 build inputs are unchanged. The AMM implementation is a captured runtime dependency, not a source template for the Pump handler.

The accepted scope is exactly one native curve per Pump CPI, hop flag 3 (both endpoint fee flags), ordinary legacy Tokenkeg 82-byte mints and 165-byte token accounts, a 166-byte ordinary curve, and no synthetic completion. It rejects unsupported multi-curve runs, other valid flag modes, non-native/nested quote branches, Token-2022 layouts, holder-reward paths and completion crossing with the explicit reconstruction-unsupported error. Complete, Mayhem and the tested cashback curves retain the captured rejection codes. No initializer, v3 extension, incentive, stopped sell_v2 fee, or shared trade helper was changed or exercised as a new experiment.

The interface, route grouping, parser and helper dependencies are established by the separate immutable static package `work/pump-multi-hop-curve-static`. The new module keeps the captured 13-account order and enforces both the AMM `global_config` PDA derivation and its signer requirement. Every runtime fixture is an ordinary test-owned outer transaction sent to the captured AMM. That captured AMM itself signs its Pump CPI. The harness never signs a PDA or marks a fabricated direct Pump transaction as trusted.

The input state is explicitly synthetic. The fixture copies saved curve/config bytes, changes the base mint and token accounts to ordinary legacy layouts, derives the corresponding legacy vault ATA, and funds local test accounts. It is not a claim that those synthetic accounts historically existed or were initialized on-chain. Captured AMM, Pump, Fees, SPL Token, Token-2022 and ATA executables are only runtime inputs, never build inputs.

## Dataflow recovered within this scope

The native buy input is transferred from the user to the curve before the base-token output transfer. The sell transfers base tokens first, then applies checked reserve/accounting mutation. Sell output zero rejects with 6022 before the input transfer. Buy fee-budget zero, remaining-budget zero and computed-base zero produce 6041, 6042 and 6020 respectively. Native buyback lamports are moved from the curve to the configured recipient WSOL ATA; the original performs a genuine self CPI with event authority, curve and recipient before SyncNative. The native sell payout to the user occurs after this buyback synchronization. The original jump from `0x5eb68 -> 0x58f58` back to `0x5e208`, followed by the direct native move at `0x5e2b0 -> 0x965b8`, supports this order. Input transfer `0x5d360 -> 0x5a260` precedes reserve update `0x5d420 -> 0xa13e0`.

Trade events use `ix_name = multi_hop_swap`; native quote, token, reserve, creator and buyback fields, the self-event CPI payload and 16-byte result match the finite fixtures. No claim is made that the unresolved TradeEvent trailing field is generally reconstructed. The module reuses the frozen event/layout types without changing their interpretation.

## Validation and preserved failures

The final fixed-config matrix has 56 unique comparisons and 112 independently verified outer signatures. Fifty comparisons reach the Pump CPI; six are rejected by the captured AMM first. Eleven comparisons succeed. Equality covers errors, complete account snapshots, event bytes, captured inner-instruction bytes and return data. Compute-unit consumption and source-location log text are excluded. The repeated final execution is verification only and does not add unique cases.

Build 01 failed with a lifetime and AccountInfo-borrow type error. Its exact source and compiler log are retained. Build 02 had native sell zero-output and lamport-update ordering differences; build 03 then exposed three low-input buy rejection differences and sell reserve-underflow timing. These negative receipts are retained. Build 04 passed the fixed matrix; build 05 adds explicit guards restricting acceptance to the layouts and flag actually covered by that matrix. All builds use a fresh target directory, the same v1.44 compiler selection and the unchanged locked dependency graph. This is not evidence of the historical compiler or dependency graph.

An early cached-harness receipt is expressly invalid for parity counting: alternating nested Pump ELFs in one cached AMM VM left the candidate active for later nominal-original runs. The diagnostic retains that harness and receipt. The replacement constructs a fresh VM for each side and loads exactly one chosen Pump executable. The existing AMM differential suites used distinct AMM cache keys; this diagnostic does not establish a failure of their historical evidence.

This is a PARTIAL instruction candidate and must add no fully recovered handler count. It has not yet been integrated onto Pump48 or subjected to all existing whole-program differential and Surfpool regressions. The previously recorded sell_v2 quote-transfer-fee mismatch is unchanged. Full original-byte equality, exhaustive behavior, historical source recovery and the security audit remain incomplete.
