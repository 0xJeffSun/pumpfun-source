# Current Fees source security applicability review

The review covers all 31 current Fees instruction entries and their local handler, account, helper, serialization, CPI-target and arithmetic code. The 31-row `COVERAGE.md` / `coverage.json` is the explicit per-path record. This is a complete pass over that source scope, not a claim that all vulnerabilities have been excluded.

No concrete unauthorized withdrawal, arbitrary CPI target, PDA signer bypass or privilege escalation is established by this pass. There is one concrete availability/configuration-persistence concern and several explicit trust/accounting boundaries requiring specification or wider evidence. None is promoted to a confirmed deployed-original vulnerability. No source change, build, target execution, fixture or live transaction was performed.

## A1 — Short FeeConfig stable-tier writes can be invisible on the next decode

**Established candidate-source consequence; authorized-operation availability/persistence concern.** `types.rs:64–74` always supplies an empty `stable_fee_tiers` vector when account data length is below 4,073, regardless of serialized bytes after the normal tier vector. `update_stable_fee_config` and `upsert_stable_fee_tiers` accept valid nonempty tiers, change the vector, and do not require or create that allocation (`lib.rs:267–289`; account contexts `contexts.rs:143–174`). `initialize_fee_config` creates only 2,512 bytes (`contexts.rs:35–45`), and the normal tier query reaches `select_fee_tier`, which indexes `tiers[0]` without an empty check (`lib.rs:305–310`).

For a short account, a normal/stable tier combination whose serialized body fits can be written successfully but the following decode still yields zero stable tiers. The exact current serialized size is `97 + 40 × (normal_count + stable_count)` bytes, including discriminator and exotic fields. Thus even a very small valid stable update fits the 2,512-byte allocation while remaining hidden by the length gate. A subsequent pump-pool stable-tier query selects that empty vector and panics; no attacker-controlled state corruption is needed for this operation sequence. `get_fees_with_quote_mint` has the same empty-vector consequence for its USDC branch. Independently, freshly initialized normal tiers are empty until configured, so a normal pump-pool query can also panic before initial setup.

All mutations require the configured admin signature; this is not an outsider write or drain. `extend_fee_config` (permissionless payer) or `set_exotic_flat_fees` (admin payer) can grow to 4,097, after which valid stable tiers can be stored and decoded. Whether growth-before-stable-update is an intended external operational contract, and whether the original program has identical behavior, remain unresolved. Do not silently change this reconstructed contract without original-path evidence. A precise specification or further original static analysis should decide whether to enforce the allocation precondition, grow on update, reject empty queries or document setup requirements.

## A2 — Social V2 reports a projected recipient balance, not an observed post-CPI balance

**Established source accounting definition, conditional integration concern.** In the token branch `social.rs:28–38`, `before` is deserialized from the destination or defaults to zero on a decoding error; the transfer uses the full source token amount; `after = before.saturating_add(amount)` is computed without reloading the destination after CPI. The event exposes that value as `recipient_balance_after` and increases `total_stable_claimed` by the nominal amount. A successful CPI alone does not prove that the arithmetic projection equals the eventual token-account balance under every supported token behavior. `Interface<TokenInterface>` admits the two standard token program IDs; the exact set of nontrivial token behaviors accepted by each called program is outside this pass. No token-extension probe, net-loss demonstration or original discrepancy is claimed. Consumers should not treat this field as an independently read balance.

A concrete conditional alias route exists in the source without relying on token extensions: the claim authority may supply `recipient == social_fee_pda.key()`, so both canonical ATA addresses coincide. No inequality guard rejects this choice. The retained SPL Token 7.0.0 source (`processor.rs:271–311`) validates a same-account transfer and returns success before changing token amounts. Under that dependency behavior, Fees still increments its nominal claimed counter and cooldown and emits the projected higher balance. This is a source-composition observation; the captured token executable was not revalidated against that crate source here and no alias transaction was executed. It demonstrates why the counter/event should not be treated as independent evidence of funds leaving custody. The configured claim authority is required, and downstream economic use of these fields remains unknown.

The native branch and legacy social claim read the actual lamport balance after the direct mutation. This distinction is visible source behavior, not evidence of unauthorized payment.

## A3 — Authority and recipient selection are explicit trust, not end-user ownership proof

**Intentional candidate policy boundaries, not reported vulnerabilities.** Both social claims require the global `social_claim_authority` signer and allow that authority to select any writable recipient; no wallet signature or cryptographic user-id-to-recipient relation is checked (`social.rs:79–121`). The FeeProgramGlobal authority can replace the claim authority, flags and cooldown; it can set zero claim authority. FeeConfig admin can set arbitrary next admin, including zero/non-signing keys (`contexts.rs:120–131`), while the global `set_authority` rejects zero. Buyback's global authority can assign zero sweep authority and any signed cooldown; the sweep authority selects the destination.

The relevant unauthorized-party tests are signer + `has_one` + owned canonical PDA constraints, not whether recipients equal an independently authenticated human. Those constraints are present. Security depends on key custody/governance and expected policies outside this source. Admin-approved lockout or redirection should not be mislabeled outsider exploitation.

## A4 — Token helper admission is narrower than a complete token policy

**Established source validation boundary.** `instructions/fee_sharing/mod.rs:17–43` validates the canonical ATA address, optionally invokes the fixed associated-token program for System-owned accounts, then checks the account's program owner and token mint. It does not separately compare the token account's internal authority field with the supplied wallet. Source spending authority is checked by the token transfer; destination control is not independently asserted by this helper. For legacy-token accounts whose authority was reassigned, address canonicality alone should not be interpreted as a current-authority assertion. This review establishes the missing comparison, not an exploitable route; recipient assignment is already claim-authority controlled, and permitted token-state transitions were not executed here.

V2 sharing passes partner accounts onward to fixed Pump CPI rather than fully verifying them locally. The crank passes unchecked relay bookkeeping/whitelist accounts onward to a fixed executable RELAY. Those external validators are necessary parts of the security contract. A finite matching CPI trace does not prove their entire semantics or every malformed-account case.

## Arithmetic, storage and ordering conclusions

- Release arithmetic has `overflow-checks = true` and `panic = "abort"` in the root workspace. `validate_fees` uses checked `u64` additions followed by `unwrap`; extreme admin input therefore aborts rather than returning `InvalidFeeTotal`. Buyback's `now - last_claimed` is signed checked arithmetic in this profile and can abort at extreme values; its counters use checked addition. Claims use saturation for cooldown differences and lifetime totals. These choices prevent silent wrapping but do not establish ideal error ABI or event semantics.
- Tier validation bounds each vector to 50 and requires strict threshold order; fee totals are capped at 10,000 after addition. New share validation bounds to 10, checks positive weights, checked `u16` sum exactly 10,000 and uniqueness. Payout preparation deliberately filters executable old recipients and rescales retained weights with bounded `u64` multiplication; already stored state validity remains an assumption of that path.
- Declared storage sizes are coherent with the ordinary types: FeeProgramGlobal338; SocialFeePda179 at at most20 UTF-8 bytes; DonationFeePda218; BuybackVault208; maximum10-share SharingConfig420 within allocated1024; maximum50+50 FeeConfig4097. Serialization can fail after state mutation/events if an older smaller FeeConfig allocation cannot hold the selected vectors. No successful-write guarantee should be inferred solely from early validation.
- Native payments derive excess with saturating subtraction and preserve the source rent bound used by the path. Withdrawal uses a System-owned PDA and a fixed System CPI, while social/buyback/donation debit owned state accounts. Adds/subtracts remain fallible/checked under the profile. No source route lets an unauthenticated caller select a different custody PDA and sign for it.
- Several paths initialize accounts before handler guards, or perform external CPI before final local validation/counter updates: buyback sweep; donation crank; sharing creation and both share updates. The review relies on the platform's transaction-failure atomicity when reasoning that later errors do not commit partial asset/state changes; it does not prove runtime atomicity from these source files. Event logs may be emitted before a later exit/serialization failure; consumers must require successful transaction status.
- Account data borrows are generally explicitly dropped or block-scoped before CPI/mutation. Raw curve helpers intentionally use infallible `RefCell::borrow` after length checks; a conflicting borrow is a panic rather than a returned error. No reachable borrow conflict is established from this static pass. Destination/source aliases and account re-use remain a reason for full error-path evidence, not an invented theft claim.

## CPI targets, PDA signers and ownership

`Program<T>` checks key and executable in the pinned Anchor implementation; `Interface<TokenInterface>` limits the selected token program ID, and `InterfaceAccount` checks supported owner plus deserialization. Generated external `Account` codecs use the declared IDL program owner. Local `Account` types use Fees' owner and discriminator. The unchecked namespace keys in query/config instructions need not themselves be executable, but they only select an owned PDA namespace and do not confer write access.

Direct application CPIs use fixed Pump, AMM, RELAY, System, Token or associated-token program IDs; generated Pump/AMM contexts are typed at admission. In particular, unchecked account fields named `program` in manual contexts are not arbitrary event-CPI targets: pinned `emit_cpi!` emits `Instruction::new_with_bytes(crate::ID, ...)` and signs only for `__event_authority`. Withdrawal signs only for `[referral-vault, user, bump]`; social tokens only for `[social-fee-pda, stored user_id, stored platform, bump]`; donation only for its stored base/config PDA; buyback only for `[buyback-vault, index, bump]`. The external PDA signer required by sharing reset is derived under Pump, in addition to its configured human/admin signer.

There is no blanket assertion that every unchecked account is safe. Exact delegated checks, optional-account failure order, forwarded remaining privileges and external program upgrade/owner semantics require the full external/runtime evidence. No transitive external audit is claimed.
