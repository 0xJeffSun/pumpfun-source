# Current Mayhem source security coverage

This review covers the 24 current source entries and their permitted local account, arithmetic, CPI and state-update code. `COVERAGE.md` / `coverage.json` lists every entry and one additional **excluded opaque** slot for `initialize_mayhem_state`. That initializer is absent from this source and was not investigated; no original initializer body, trace, runtime or prerequisite-state construction was read or executed.

No unauthorized asset extraction, arbitrary CPI target or PDA signer bypass is established by this review. There are concrete bootstrap, risk-accounting and failure-domain properties requiring explicit deployment/policy assumptions. They are candidate-source findings or conditional concerns, not confirmed deployed-original vulnerabilities. This is a source coverage pass, not an exhaustive security proof.

## M1 — First caller controls a fresh GlobalParams bootstrap

**Established candidate-source authority policy; deployment applicability conditional.** `InitializeGlobalParams` requires only an arbitrary signer payer and initializes the canonical `[global-params]` PDA; the handler stores that signer's key as admin. There is no fixed administrator, existing-authority proof or other ownership gate. On an uninitialized deployment, the first successful caller becomes admin. Once initialized, the `init` constraint prevents another caller from replacing it through this entry.

This matters to deployment sequencing and to any proposed fresh deployment of the candidate. It is not a takeover of an already initialized deployed program, and this review establishes neither live initialization state nor the original historical bootstrap policy. The `initialize_fee_recipient` entry likewise permits any signer named `admin`; it does not require `global_params.admin`. It only creates a canonical indexed fee account and its WSOL ATA and sets bump/index, so the payer is not given withdrawal authority by that entry. Index precreation is an explicit source capability, not a demonstrated theft route.

## M2 — Risk caps truncate positive signed counters to the low64 bits

**Established comparison semantics; bypass reachability unproved.** All three buy families accumulate global/per-coin deployment in checked `i128`. After a successful CPI and reload, they test whether the signed counter is positive, then compare the configured `u64` limit with `counter as u64`. Above `u64::MAX`, that cast uses only the low limb; the source does not enforce a full-width upper bound first. Therefore these conditions are not equivalent to `counter < limit` over the full positive `i128` domain.

A real risk-limit bypass would require a reachable sequence that crosses into that range while satisfying all preceding state, available-balance, trade-size, external-CPI and post-call checks. This review provides no such sequence. The excluded initializer's state domains remain opaque, and no new transaction was constructed. The safe conclusion is that a full-width range invariant is required to justify interpreting the current guard as an absolute exposure cap. The exact source comparison is retained intentionally, and no unreviewed corrective rewrite is proposed.

The risk values themselves use raw quote amounts. WSOL and the default-key accounting branch feed `sol_deployed`; other quotes share `stable_deployed`, while each coin has one `field_56`. They are not automatically value-normalized between differently denominated quote mints. A deployment that permits several quotes requires an external unit/currency policy before treating the aggregate as a common economic exposure measure.

## M3 — Trusted parameters include aborting and disabling values

**Established failure-domain/policy boundary, not outsider escalation.** All trade families evaluate `10_000u16 - retained_reserve_bps` without an explicit <=10,000 check. Larger trader-provided values abort under the checked release profile. Timestamp cooldown checks use signed `last + interval`; admin-written interval bytes can represent negative or overflow-producing signed values. Price-band arithmetic uses checked operations and can return an error for extreme reference/tolerance pairs. Several conversion/division and `Clock::get()` paths intentionally unwrap.

Trade price bands are evaluated against a reference supplied by the authorized trader; the source does not fetch an independent price oracle. Caps and reserve-retention values are risk controls only under that delegated trader policy. Admin setters allow zero replacement admin/trader and arbitrary cap/opaque-field values. `reset_state` clears selected policy bytes and counters while unpausing; it preserves admin/trader/max-sweep fields and can leave zero purchase risk limits. These are explicit administration capabilities requiring policy review, not evidence that an unprivileged caller can modify them.

The sweep loop also uses ordinary `u64` subtraction/addition for remaining cap, rent excess and lifetime counters. With valid rent and bounded running totals, the intended cap is maintained; malformed/underfunded or extreme lifetime states may abort rather than return a typed error. No such state was created here.

## M4 — Extension payer mutability is not declared in the client context

**Concrete source/client usability boundary.** `ExtendAccount.user` is a `Signer` without `#[account(mut)]`, yet a positive rent shortfall uses it as the System transfer source. An actual funding transaction needs writable privilege. A caller can supply that privilege even when the parser does not demand it, but a client using the generated read-only meta may fail the CPI. This is not an authorization bypass or a committed loss; no transfer was run to confirm a particular generated client failure. The existing source and original account-meta contract would need review before adding a mutable constraint, which could change accepted error order.

## Authorization, custody and CPI applicability

- Administration, pause/reset, cap and key updates use the owned canonical GlobalParams PDA and `has_one=admin`; trade and capped sweeps require its configured trader signer. Admin withdrawals additionally bind the shared `[sol-vault]` PDA. Token withdrawals bind both source-vault and destination-admin ATA relationships.
- Trade custody accounts are derived for that sol-vault PDA and the selected mint. The external Pump curve is owner-checked and mint-seeded. PumpSwap pools/global config are owner/discriminator-checked but their pool/mint/vault relationships are mostly delegated to the fixed external AMM call. No arbitrary external executable is selected: source CPIs use fixed Pump/AMM IDs and constrained token programs, with signatures only for `[sol-vault,bump]`. External unchecked fee, sharing, volume, creator and recipient accounts remain an external validation boundary.
- `CheckedSystemProgram` explicitly checks the all-zero System ID before delegating executable validation. This avoids treating Anchor1.0.0's `Program<()>` all-zero marker behavior as permission to use any executable. Self-event CPIs use `crate::ID`, not an unchecked account named `program`.
- `burn_tokens` is intentionally permissionless once the stored deadline has passed and state is not Ended. It burns the entire canonical vault token amount, emits events, then marks Ended. It does not consult the global pause/trader setting. Whether a stored deadline/status/mint combination is initially legitimate is part of the excluded state-initialization domain, not established here.
- Sweeps require exactly16 remaining accounts and parse8 FeeRecipient/token pairs. They do not locally require unique indices or a one-of-each set. Token transfers use each stored index/bump PDA signer, and selected destination mint/authority is constrained. Native movement is from a Mayhem-owned FeeRecipient. An ability to manufacture other owned valid recipients is not demonstrated. Repeated pairs do not by themselves increase the cumulative cap because actual balances are reread on each iteration; no general alias safety claim follows.
- Anchor1.0.0 checks duplicate mutable serializing account fields by default, but this does not cover every unchecked account, remaining-account pair or runtime alias. The custom System wrapper correctly contributes no serializing mutable key. Additional alias reachability must be assessed separately from the simple ownership constraints.

## Accounting and failed effects

Trade handlers use actual post-CPI reloads and custody balance deltas to update signed deployment/token counters. Unexpected direction or native rent effects can cause checked unsigned subtraction failure; the source assumes the called operation produces the expected balance direction. Buy families and V2/AMM sell families often replace external errors with their own `PumpCpiFailed`; legacy sell propagates the external error. These differences are retained behavior, not interchangeable wrappers.

Timestamp/status writes occur before price sizing and CPI. Risk checks occur after successful external trades. Native PumpSwap buys wrap quote SOL and later close the temporary WSOL account; sells close it after the trade. Burn emits before assigning final Ended status. A later failure must revert prior writes/transfers under transaction atomicity; this source review does not re-prove the runtime's rollback enforcement. Logs from a failed instruction are not evidence that those writes committed.

Typed `Result::unwrap` corrections in the two PumpSwap sizing expressions are already in the bound source. Their original-versus-candidate diagnostic work does not establish whole sizing equivalence. In the admitted arithmetic domain `vt>0` and `tokens,vs` are `u64`, so `floor(vs*tokens/(vt+tokens)) < vs` for positive `vs`, and equals0 for `vs=0`; subsequent caps cannot increase it. This explains the bounded zero-divisor equality path and preserves the earlier strict-guard limitation. It does not recover the excluded initializer or prove every external pool/curve invariant.

## Serialization and excluded domains

GlobalParams, FeeRecipient and MayhemState are owned Anchor accounts with explicit serialized layouts. Opaque bytes and neutral state names must not be mistaken for recovered high-level policy semantics. `extend_account` can grow supported owned discriminators and preserves larger accounts without decoding their entire fields. External SellCurve and SwapPool decoders deliberately pad short historical forms; those policies differ from the strict burn codec and do not mean arbitrary ownership/discriminator checks are absent.

No claim is made about `initialize_mayhem_state`: its authorization, state creation, data ranges and original behavior remain opaque. Likewise, the review does not prove live authority custody, external program upgrade trust, complete token behavior, all borrow/alias cases, original full-function/data identity or all unreachable malformed states. Those gaps are explicit prerequisites to a stronger security claim rather than reasons to invent a vulnerability or a speculative patch.
