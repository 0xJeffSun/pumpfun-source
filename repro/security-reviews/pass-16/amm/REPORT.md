## A1 — V2 and multi-hop sells lack the legacy reserve-liability guard

**Concrete missing source condition; conditional conservation concern, reachability/economic severity unresolved.** `legacy_sell::execute` explicitly rejects when `quote - lp_fee > pool_quote_amount - old_accrued_fees`. The analogous V2 sell and AMM multi-hop sell calculate prices using `pool_quote_amount + virtual_quote_reserves`, check that old liabilities initially fit, perform token payouts, and add new liabilities, but do not impose that same bound before completion.

Let `R` be the pre-sell quote vault amount, `F` old protocol+creator liabilities, `Q` curve quote, `L/P/C` new LP/protocol/creator fee amounts, and `B` the buyback part of `P`. Ignoring token features for this algebra, the outgoing user quote is `T = Q - L - P - C`; buyback pays `B`; the new liabilities are `F' = F + P - B + C`. Thus the final unencumbered quote is exactly:

`R' - F' = (R - T - B) - (F + P - B + C) = R - F - Q + L`.

The required nonnegative free-reserve condition is `Q - L <= R - F`, precisely the legacy guard. A token CPI requiring enough gross balance to pay `T` and `B` is weaker because it does not reserve `F'`. If effective virtual reserves `virtual_quote_reserves + F <= 0`, the usual curve bound can suffice; with a positive effective virtual component, that simple implication fails. `init_boost` can set a positive virtual component, and `trade::prepare` rejects cashback but does not exclude boost/positive virtual reserves. Multi-hop AMM legs exclude mayhem and cashback but do not exclude boost.

This is a proof gap and candidate condition to resolve, not a demonstrated exploit: integer rounding, precise reachable pool states, fee schedules, user balances and all downstream checks have not been combined into an accepted transaction. No new numerical fixture or runtime probe was created. Current-source line references and the complete three bodies are in the coverage/evidence files. The deployed original may have the same behavior or another constraint; neither has been established here. Any correction must be supported by original-path evidence and preserve admitted ordering, rather than silently imposing a new economic contract.

## A2 — Incentive schedule arithmetic has admin-controlled unvalidated preconditions

**Established candidate-source availability boundary.** AMM `incentives::admin` assigns the new mint and `seconds_in_a_day` before its optional start/end block. When both start/end arguments are zero and token supply is zero, the routine does not require a positive day period or revalidate old schedule length against the new period. Negative periods can therefore be accepted in source on that path. Claim later converts that signed period to `usize` with `expect`; zero periods skip the updater, while incompatible positive periods can make array indexes exceed the 30 buckets. Admin branches also use signed multiplication/subtraction and division before all index accesses have explicit range guards.

The signer is the configured admin on the canonical GlobalConfig; this is not an outsider write. Overflow checks and panic-abort stop wrapping but do not supply a recoverable domain error. Whether zero/sentinel schedule inputs are intentional, and what operational contract callers must satisfy, need specification/original evidence. An admin-approved negative/incompatible schedule can impair claims under the visible source; no malformed schedule was executed in this pass.

## A3 — Local legacy buys do not accrue new incentive volume

**Established local dataflow, intended behavior unresolved.** The `track_volume` argument is passed into `legacy_buy::execute`, but its only downstream use is the event field. The handler sets the accumulator's user key; it does not increment `current_sol_volume` or a global `sol_volumes` bucket. Multi-hop and V2 trades similarly emit or read accumulators without adding fresh trade volume. The AMM claim routine consumes existing `current_sol_volume` and clears it; the admin routine resets or reads global bucket arrays.

This means this source alone does not establish functioning new volume accrual for the advertised tracking flag. It does not show lost tokens, original non-equivalence or a vulnerability: external/preexisting state may be the intended source, or active tracking may be outside the recovered behavior. An event carrying `track_volume=true` should not be treated as proof that a reward bucket was credited. Complete original active-schedule dataflow and intended feature policy are missing.

## A4 — Metadata creator vector is indexed without a nonempty check

**Conditional candidate availability issue.** `creator_reassignment::set` treats `metadata.creators == Some(...)` as sufficient to read `creators[0]`. A deserializable `Some(empty)` vector panics rather than taking the bonding-curve fallback or returning a domain error. The metadata address and owner are constrained, and the pool must be canonical with no existing creator. Whether the live metadata program permits or has produced such a value is not established; this pass did not open a new Metaplex runtime lane. The first creator's `verified` bit is also not consulted. That is a visible attribution policy, not by itself proof of unauthorized control.

## Authority, account ownership and CPI conclusions

- Admin operations require a signer matching the owned GlobalConfig's admin. Some contexts also require the canonical `global_config` PDA; others rely on ownership/discriminator and the source invariant that the sole config initializer uses that PDA. The absence of a repeated seed check is not automatically a counterfeit-account vulnerability; proving such a route would require an alternative valid account writer or runtime ownership failure.
- Pool contexts generally bind mint/LP/vault keys through `has_one`; token transfer/mint/burn CPIs enforce current token account/mint authority. Outgoing custody operations derive the pool signer from the stored pool tuple/bump. Several contexts omit an explicit pool seed check, so correctness also relies on that signer verification and the restricted account-creation paths. No attacker-created nonzero AMM-owned Pool is demonstrated.
- User-authorized trade/liquidity debits use the user signer; claims and creator collection intentionally permit anyone to trigger payment but constrain the destination to the recorded user's or creator's token authority/derived vault. Cashback claims do not require a user signer; their token destination is still authority-checked. Closing a user accumulator requires its user signer, so forfeiting unclaimed state is an authorized choice, not a third-party close route.
- Fee recipients are constrained by the configured recipient set and canonical ATA relationships. V2/multi-hop buyback checks include token-program owner, mint, internal authority membership and canonical address. Legacy creator/cashback remaining-account validation may happen after other transfers, so final success cannot be inferred from a partial CPI trace.
- Direct CPI targets are fixed AMM self/System/SPL Token/Token-2022/ATA/Fees/Pump IDs or typed interfaces. Legacy fee-return decoding does not compare the returned producer ID; it relies on the immediately successful fixed Fees invocation. Multi-hop explicitly checks Pump producer and 16-byte return layout and checks selected actual balance deltas. Native Pump transition checks are narrower and delegate semantics to the fixed external program.
- Multi-hop signs only the canonical global-config PDA and, when needed, the previous pool tuple; it verifies continuous mint direction before execution, parses AMM groups with owned account types and serializes each hop before continuing. Forwarded Pump contexts and arbitrary account alias combinations still require external/runtime evidence. A correct named-account list does not close that whole contract.
- Unchecked event `program` fields do not choose an arbitrary event target. The pinned event macro constructs a CPI to `crate::ID` and signs the canonical event authority. The custom multi-hop event helper likewise uses the fixed AMM ID.

## Conservation, arithmetic, serialization and failed effects

The source uses `u128` products and explicit `u64`/`i128` conversions for most swap/reserve math, checked fee/counter additions and root `panic="abort"` / `overflow-checks=true`. Individual global fees are capped at1,000 bps, and configured buyback at10,000; per-pool creator overrides and max-configurable bounds are separately privileged and not uniformly clamped by pool creation. These checks prevent routine silent overflow but do not prove economic invariants for every owned legacy state.

Pool creation uses actual reloaded deposited balances to compute square-root initial liquidity and locks100 LP units. It admits only legacy tokens or Token-2022 mints with metadata-related extensions. Consequently, base-transfer-fee assumptions in trade/liquidity source may be safe for newly created pools under that narrow policy but cannot be generalized to all historical or externally introduced states. This report does not treat a hypothetical extension-bearing pool as a demonstrated reachable exploit.

Ordinary withdrawal excludes accrued liabilities from quote reserves and checks LP mint supply does not exceed tracked supply. Self-transfer helpers check internal source authority when source/destination alias, so a bare alias is not automatically a free deposit. They do not establish all many-account alias combinations; no blanket alias safety claim is made.

GlobalConfig and Pool codecs choose size-based historical layouts and zero-pad absent tails in memory. Serialization writes the full current structure. Updating an old short allocation without a resize can fail account exit after handler logic/events. Resize-capable handlers extend before writing. `extend_account` is permissionless but requires AMM ownership and a supported discriminator and sends the caller-funded rent delta only to that account. These are availability/ordering facts; no unauthorized data overwrite was shown.

Many operations transfer or allocate before later validation, mutate counters after a CPI, or emit before a subsequent harvest/close/serialization step. The assessment of no committed partial movement on error relies on transaction atomicity enforced by the execution platform; source inspection is not a proof of that runtime property. Logs from a failed transaction must not be used as proof of finalized state. `boost_buy_and_burn` intentionally emits before its final optional writable-mint/harvest/close operations; later failure remains significant to receipt consumers.

## Vendored formatter provenance and security scope

`formatter_check.py` independently compared every current vendor file with the retained published solana-pubkey2.4.0 archive, SHA-256 `9b62adb9c3261a052ca1f999398c388f1daf558a1b492f60a6d9e64857db4ff1`. Only `Cargo.toml` and `src/lib.rs` differ; `formatter.patch` preserves the exact delta. The manifest adds already-locked bs580.5.1 with default features disabled. The implementation replaces the formatter with a44-byte stack buffer, base58 encoding, checked UTF-8 conversion and `write_str`; `Debug` and `Display` share it. All other archive members, including PDA derivation and parsing implementations, match bytewise.

The two `unwrap`s operate on fixed32-byte public keys and a buffer sized for the maximum44-character encoding; the emitted alphabet is ASCII. No arbitrary byte string is interpreted as unchecked UTF-8 by the replacement. The retained static renderer record supports bounded normalized matching to the original renderer but is not a full indirect-call/data or original-dependency proof. The archive provenance and license are not a claim that solana-pubkey2.4.0 was the deployed historical version. No formatter/compiler search or new execution occurred.
