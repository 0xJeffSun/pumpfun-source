The packet inventories every one of the53 current dispatch entries and separately records two absent excluded incentive entries. `COVERAGE.md` and `coverage.json` contain the per-entry account, authority, effects and scope records.

This is a **permitted-source review**, not an exhaustive audit. No deployed vulnerability or unauthorized drain is established. ## P1 — Cashback V2 selects a token CPI target through an unchecked account

**Established local trust-boundary gap, exploitability unresolved.** `ClaimCashbackV2.quote_token_program` is unchecked. For the token branch, the handler checks `quote_mint.owner == quote_token_program.key()`, deserializes mint bytes, checks destination program owner and internal user authority, then invokes `transfer_checked` using that supplied target and signs for the canonical user-volume-accumulator PDA. It does not locally require the selected program to be one of the standard token program IDs.

This differs from an `Interface<TokenInterface>` admission. It is not sufficient to claim an arbitrary-program exploit: the source token account address is constrained as an ATA under the fixed associated-token program, its data must yield a positive balance, and the signed CPI receives only the specified mint/source/destination/authority accounts. Constructing such a source for a nonstandard token target requires external account-creation/ATA reachability that was not established here. No hypothetical target was deployed and no transaction was constructed. The appropriate conclusion is that local target admission alone does not close the trust boundary; it needs explicit external proof. It does not establish the ability to spend an unrelated user's funds.

## P2 — Metadata first-creator indexing requires a nonempty external vector

**Conditional availability/attribution property.** Both `set_creator` and permissionless `set_metaplex_creator` select `cs[0].address` when `metadata.creators` is `Some`. There is no empty-vector guard and no check of the selected creator's verified flag. If an admitted metadata account has `Some(empty)`, the source panics; if it has a first unverified creator, that address is still the source-selected creator. The metadata account's canonical PDA, program owner and parser are checked. Whether that external metadata state can legitimately occur, and whether this attribution policy matches the original, remain outside this pass. No additional Metaplex runtime investigation was performed.

The creator checkpoint now uses the complete BondingCurve decoder/serializer for migration/setter/sync paths. Its decoder admits historical shorter layouts, while serialization emits the complete current fields. A mutating creator call on an allocation too short for the complete serializer can fail at exit unless a preceding operation has extended the account. This is a source-level allocation precondition, not proof of data corruption or an original mismatch. Existing finite creator cases did not add a new short-allocation test. Setter early returns for a nonzero creator preserve the prior state; migration checks holder immutability and zero accrued creator fees before changing the creator.

## P3 — Fresh global initialization is a first-caller authority policy

`initialize` accepts any signer payer, creates the canonical global PDA and stores that user as authority. It does not require a fixed deployment administrator. On a fresh uninitialized deployment, the first successful initializer controls administration; the `init` constraint prevents a subsequent replacement through that entry. This is a bootstrap policy concern, not a claim about the already initialized original deployment. Live state and intended deployment sequencing were not inspected.

Quote-control initialization is also permissionless, but it initializes both control authorities to zero. Global authority subsequently assigns its admin, and admin/global/reserves-admin rights are explicitly separated across setters. Thus first quote-control creation alone does not confer reserve-administration privilege. Global authority rotation allows arbitrary next keys, including zero; such lockout choices are privileged and should not be mislabeled external takeover.

## P4 — Rewards and V3 fee/settlement completeness remain unproved

The permitted legacy buy source emits `track_volume` but does not itself increment global/user trade-volume counters; V3 paths emit fixed false/zero volume fields. The excluded reward administration/claim lanes and their complete integration were not reviewed, so this packet does not conclude that reward accounting is complete or defective. A recorded tracking flag is not proof of accrued entitlement.

V3 buys retain known reconstruction limitations: the fee account is unchecked at the context level apart from owner/PDA, decoded later; the original typed admission/four-zero whitelist bypass is not integrated; `buy_v3` discards its `partial_fill` argument. The allowed source correctly distinguishes normal mint supply from Mayhem curve supply for the buy fee basis, and the current buy guard order rejects complete before cashback. These local facts do not prove the full original settlement/error/reload/extension closure. No excluded V3 token-extension work was reopened to fill that gap.

## Authorization and custody conclusions

- Global administration uses the owned canonical global PDA and configured authority signer. `set_params` checks sorted unique nonzero rent-exempt recipients, reserve relationships, each fee<=1,000, nonzero withdrawal key and migration-fee bounds. Other global settings, creator maxima and quote reserve values are trusted admin policy, not independently price-validated.
- Creator assignment has separate configured set-creator/admin-CTO authorities. Permissionless creator migration requires a Fees-owned canonical sharing config with matching mint/admin; it does not locally require active/unrevoked sharing status. That is a visible dependency-policy boundary, not proof of malicious migration. Administration and migration also depend on external Fees/AMM checks and their owners.
- Creator collection and cashback claims are intentionally permissionless triggers with recipient/vault derivation or token-authority constraints. Holder-reward distribution instead requires the configured holder-reward claim authority, which chooses recipients and amounts; this source does not independently prove holders' real-world entitlement.
- Fee distributions require owned canonical curves and Fees-owned sharing state, correct creator relation and recipient keys/nonexecutable/positive shares. They do not locally revalidate total share weight/uniqueness and therefore rely on the external Fees writers. Invalid external weights may overdraw and fail, rather than proving a compliant payout. Rounding uses a fixed denominator of10,000; remaining dust is not silently assigned elsewhere.
- Migrations are permissionless paid triggers, not withdrawal-authority-signed calls; the global-configured withdrawal address is the destination for leftovers. Source/target vaults, pool, authority, mint and event PDAs are derived, and external AMM calls use fixed typed program identity. The captured behavior includes account creation/asset moves before later validation; failure atomicity is material.
- Most token CPI targets are fixed programs or standard token interfaces. Self-event macros target `crate::ID`. The raw migration helper uses a typed self `Program<PumpRecovered>` for its event call, so its dynamic-looking `program` variable is not an unchecked target. P1 is the separately identified unchecked cashback case.

## Conservation, failure order and source-domain limits

Most allowed trade formulas use widened `u128` products, checked add/subtract and explicit narrowing. Reserve and fee liability updates distinguish native lamports from token quote balances. Legacy trades and creator distributions rely on real token/System calls for final authority, ownership and fund availability. The local source does not establish all token behaviors: base token transfer assumptions, quota units, zero balances and every many-account alias require dedicated admitted evidence.

The V3 and shared curve preparation code funds the rent deficit using native reserve+accrued-fee liabilities before reallocating. Full/partial codecs intentionally handle old account lengths differently. The creator migration/setters now preserve full named and trailing fields through the shared codec; `admin_cto` still uses its distinct partial view/raw field writes and has a larger external call closure. Those contexts are not interchangeable proofs merely because they all name a curve.

Several paths transfer assets, fund ATAs, emit events or mutate memory before a subsequent validation, arithmetic operation, Clock read or account-exit serialization can fail. No committed partial-loss conclusion is drawn from that source order: the assessment relies on platform transaction rollback. Conversely, an emitted event from a failed transaction is not proof of committed state. Overflow checks and panic-abort stop wrapping but do not make every failure a recoverable domain error.

CreateV2 deliberately rejects Mayhem creation in the current reconstruction and restricts cashback; nested quote creation includes bounded ancestor-depth and account owner/key checks, with stated source-hypothesis limits. The multi-hop curve path explicitly fences ordinary Tokenkeg/noncompleting/non-Mayhem/non-holder domains. Its source comments and guards must not be presented as historical behavior for excluded domains. General route safety, arbitrary cycles/aliases and omitted extension adapters are not certified here.
