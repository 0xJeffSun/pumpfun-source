# ATA historical build provenance follow-up

No new build recipe is sufficiently supported to justify another build. No builds, binary edits, main-source edits or flag/metadata searches were performed. The closest saved candidate still differs at307 byte positions; correspondence after swapping two RawVec specializations is diagnostic, not byte identity. Timestamp-supported candidate5 recreated candidate3 and differs at1,506 positions.

## Concrete findings

1. The saved official release metadata gives an Anchor verification recipe using Solana1.10.33, Debian bootstrap and ubuntu:20.04. It does not identify the original compiler invocation, lockfile mutation, host Cargo version or uploaded artifact's CI run. The upload precedes the later version-bump commit, as prior chronology already established. [Official release](https://github.com/solana-labs/solana-program-library/releases/tag/associated-token-account-v1.1.0).
2. The candidate2 source's actual Anchor.toml pins **Anchor0.24.2**, not0.25.0. I inspected both; the relevant container invocation is materially the same: mount workspace at `/workdir`, use `CARGO_TARGET_DIR=/workdir/docker-target`, invoke cargo build-bpf with a relative manifest, install Rust through an unpinned rustup bootstrap when Debian bootstrap is requested, and install the specified Solana release. Saved builds instead use pinned verifiable-image host Rust1.59 and direct `/build` invocation. This is a concrete recipe difference but not proof of a changed mono-item ordering. [Pinned Anchor configuration](https://github.com/solana-labs/solana-program-library/blob/f5ce86d43dd31ddefb96d4e8cdd67dd073dc5dca/Anchor.toml), [Anchor0.24.2 implementation](https://github.com/coral-xyz/anchor/blob/v0.24.2/cli/src/lib.rs).
3. **A mount-path experiment is not justified by Cargo metadata alone.** Cargo0.60's compute_metadata hashes package source relative to the workspace, features, dependency metadata, profile/mode/LTO, target and compiler identity. SourceId::stable_hash explicitly removes the workspace path prefix. The target output directory is not among those metadata inputs. Thus `/build` versus `/workdir`, while a factual invocation difference, does not establish the proposed cause for the two RawVec symbol hashes. This statement concerns these metadata functions; it does not assert that all compiler-generated bytes are path-independent. [Metadata implementation](https://github.com/rust-lang/cargo/blob/0.60.0/src/cargo/core/compiler/context/compilation_files.rs), [SourceId hashing](https://github.com/rust-lang/cargo/blob/0.60.0/src/cargo/core/source/source_id.rs).
4. Official token CI runs token tests before ATA tests in the same workspace; afterward it uploads target/deploy/*.so. Its wrapper sets RUSTFLAGS=-D warnings and chooses stableRust1.59.0. This establishes the order of CI commands and artifact location, not that the release uploader used that particular job. The prior candidate4 already tested the warnings flag, and prior investigation established that test-bpf does not add its host-test feature to the BPF build. Repeating those flags is not new evidence. [Workflow](https://github.com/solana-labs/solana-program-library/blob/f5ce86d43dd31ddefb96d4e8cdd67dd073dc5dca/.github/workflows/pull-request-token.yml), [wrapper](https://github.com/solana-labs/solana-program-library/blob/f5ce86d43dd31ddefb96d4e8cdd67dd073dc5dca/ci/cargo-test-bpf.sh).

## Bounded recommendation

Keep the307-position candidate as the best result and do not launch a mount-path, arbitrary-version or metadata search. The strongest missing evidence is the release uploader's actual archived build log or CI artifact association: exact source/lockfile, feature graph, host Cargo/BPF Cargo versions and rustc invocations (especially spl_token_2022 -Cmetadata). Such evidence could select one concrete historical recipe and explain specialization ordering. The release command alone cannot recover those missing inputs: its Debian bootstrap fetched then-current Rust and is not a hermetic historical specification.

The downloaded upstream source files and git-show snapshots are preserved beside this report with URL/SHA256 provenance in sources.json. No claim that the candidate was independently reproduced byte-identically is made.
