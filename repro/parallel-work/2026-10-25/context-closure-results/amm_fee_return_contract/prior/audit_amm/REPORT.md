## Concrete candidate conclusions

**Authorization:** existing typed state supplies owner/discriminator authentication; this is not canonical-address authentication. Pool outgoing CPIs use `[pool,indexLE,creator,base,quote,bump]`, and pool `has_one` checks bind the mints and vaults. Creation establishes the vault ATA/LP authority relationships. Most trading/admin contexts omit a global-config seed check, while multi-hop, boost and incentive-admin contexts include it. Missing `create_config` means alternate valid configuration reachability and initial admin authority are unproved; absence of a seed annotation alone is not a demonstrated authorization bypass.

**Fees and reserves:** with actual quote reserve R, virtual V and accrued protocol+creator F, v2/hop accrual increments F and decrements V by the same amount. A sweep removes the paid bucket from F, adds it to V and debits R, preserving pricing reserve R+V and effective virtual V+F. [trade.rs:220–241](inputs/programs/pump-amm/src/trade.rs#L220), [sweep.rs:76–148](inputs/programs/pump-amm/src/sweep.rs#L76). Deposits ceil proportional inputs; withdrawals floor outputs; quote reserve excludes accrued fees. LP creation retains100 accounting units. These are meaningful local invariants, conditional on authentic initialized state, supported assets and actual token-program behavior.

**Recipient safety:** permissionless cashback/creator claim/sweep and fee forwarding bind destinations to the user, creator, configured recipients or their PDAs/ATAs. Lack of a user signature in those payout paths is not itself a theft condition. Generic quote-token counters aggregate gross units across mints and can include donations; they must not be read as a single-asset net financial ledger. [cashback.rs:4–29](inputs/programs/pump-amm/src/cashback.rs#L4), [collect.rs:5–24](inputs/programs/pump-amm/src/collect.rs#L5), [transfer_creator.rs:5–60](inputs/programs/pump-amm/src/transfer_creator.rs#L5).

**Atomicity:** several handlers perform rent or token CPIs before all validations, and emit before serialization/close. All errors propagate rather than being caught and suppressed. Conditional on normal Solana transaction rollback, failed later work does not commit earlier payouts. Failed-transaction logs still exist and are not settlement evidence. This review did not reverify runtime rollback or loader semantics.

## Multi-hop guarantees and remaining trust

[Route scan219–255](inputs/programs/pump-amm/src/multi_hop.rs#L219) consumes exactly five accounts per hop, checks nonempty divisibility, mint continuity, uniform buy/sell direction, and final mint. AMM groups go through typed `AmmHop::try_accounts`, then canonical-pool/cashback/mayhem checks. Input comes from the user or prior pool authority; seeds are generated internally from authenticated Pool state. Intermediate AMM results remain in vaults until the next hop transfers them. Each hop explicitly serializes before the next one, so duplicate appearances do not automatically imply stale state; unusual aliases still need a full conservation proof.

[Pump run283–347](inputs/programs/pump-amm/src/multi_hop.rs#L283) constructs a fixed thirteen-account prefix plus the original groups, passes endpoint protocol/creator flags, signs only AMM global config and the internally selected source authority, and invokes fixed PUMP. [Return validation348–393](inputs/programs/pump-amm/src/multi_hop.rs#L348) requires PUMP and16 bytes (output,buyback u64), compares nonnative source/destination balances with alias/buyback adjustments, then treats the next AMM input as prepaid. Final output amount must meet minimum at434. These are caller-side guarantees, not proof of complete native/Pump semantics or captured-original route equivalence.
