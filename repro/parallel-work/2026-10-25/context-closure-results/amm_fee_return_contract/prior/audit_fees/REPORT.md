## Concrete review conclusions

- Ordinary FeeConfig writes require its stored admin signer, correct owner/discriminator and namespace PDA. Global settings require the stored authority. The global initializer additionally requires the authority in a canonical Pump-owned Global, using the current **inline** `Account<Global>` context. The two deprecated handlers have no state effects.
- Social claims deliberately trust one configured signer to choose a recipient; social creation does not authenticate a social identity. This is a trust boundary, not evidence of an outsider payout bypass. Native claims retain rent and refuse executable recipients; token claims derive canonical ATAs and delegate actual transfer authorization to the token program.
- Donation initialization authorizes the current canonical pool creator or active unrevoked sharing admin. Cranking is permissionless but fixes the relay target and delegates the donation PDA signer. The relay's unchecked account relationships are an unresolved external boundary.
- Buyback initialization does not give the permissionless payer authority. The vault begins with zero authority; global authority must configure it. Sweeps require vault authority and canonical token accounts. Referral withdrawals bind signer, user PDA and token owner/mint/program without requiring canonical ATAs.
- Sharing creates and serializes the interim admin appropriate to each external migration. Updates pay old shares through fixed Pump/AMM targets before installing validated new shares and revoking admin. The retained Pump candidate confirms grouped recipients then ATAs, so the local first-N recipient check is **not** evidence of a stride-index bug.
- Event CPI target injection is **not** established: retained `emit_cpi!` source fixes `crate::ID` and signs the event PDA. The unchecked account called `program` does not choose that target.

## Scratch observations for parent review

These are candidate behaviors and unclosed security questions, not disclosed vulnerabilities in captured originals. No severity/exploitability claim is made. Preconditions, impact bounds and prerequisites are also in [findings.json](findings.json).

**F1 — Empty-tier availability boundary.** [Initialization](inputs/programs/pump-fees/src/lib.rs#L121) lines121–132 sets bump/admin but no tiers; [selection](inputs/programs/pump-fees/src/lib.rs#L303) lines303–309 indexes `tiers[0]`. A valid newly initialized config therefore has a source-reachable quote panic when `is_pump_pool=true`. A normal-tier setup alone also leaves stable quotes empty. Flat queries do not take this path. Impact established in the candidate source is failure of that quote invocation; market-wide outage or loss requires a consumer using this not-ready config. Next prerequisite: establish the intended initialization sequence and exact historical consumer/config identity, then reconcile with existing permitted receipts. No new test was run.

**F2 — Short FeeConfig stable writes do not round-trip.** [Decoder](inputs/programs/pump-fees/src/types.rs#L65) lines65–76 suppresses stable tiers below4073 bytes, while [serializer](inputs/programs/pump-fees/src/types.rs#L50) lines50–57 writes them regardless of length. [Stable update](inputs/programs/pump-fees/src/lib.rs#L265) lines265–272 does not resize. An authorized small stable update to a fresh2512-byte account fits but is ignored on next decode; a later full serialization from that decoded value can erase it. Exact full serialization size is **97+40(N+M)** bytes; 50+50 requires4097, and both arrays individually passing<=50 does not ensure short-account capacity. This is a candidate representation inconsistency with an authorized path, not an unauthorized write. Extending to4097 first removes this length gate. Next prerequisite: determine supported layout/state transitions from existing historical evidence and intended client ordering before deciding whether to preserve or patch reconstruction semantics.

**F3 — Funding signer writability is not declared on two paths.** `ExtendFeeConfig.user` ([contexts.rs](inputs/programs/pump-fees/src/contexts.rs#L8) lines8–16) and `ClaimSocialFeePdaV2.social_claim_authority` ([social.rs](inputs/programs/pump-fees/src/social.rs#L101) lines101–119) are Signers without `mut`, yet may fund System/ATA CPIs. Transactions explicitly granting writable privileges can succeed; declaration-driven callers granting readonly privileges can fail on growth or absent-recipient-ATA paths. This does not bypass authorization and is not a claim that every invocation fails. Next prerequisite: inspect the exact consumer account metas and retained failing/successful receipt cases; no new fixture is proposed here.

**F4 — Token accounting is gross, shared and sometimes synthetic.** Social v2 [lines19–32](inputs/programs/pump-fees/src/social.rs#L19) sets `recipient_balance_after=before+amount` without reload and sums all non-native mint units into one stable counter. Buyback [lines12–20](inputs/programs/pump-fees/src/buyback.rs#L12) sums all non-wSOL mint units into token2. Actual transfer-fee/hook behavior is not locally modeled. Separately, buyback permits destination=vault; sequential SOL debit/credit can net to zero while claimed counters and cooldown advance, but only a vault-authorized signer can request it. These observations concern metric fidelity and availability; theft is not established. Next prerequisite: retain exact accepted mint-extension contracts, downstream event consumers and their unit assumptions. Do not infer that TokenInterface acceptance means all extensions are supported.

**F5 — Successful old-share distribution does not prove full settlement.** Fees [sharing_update.rs lines8–35](inputs/programs/pump-fees/src/sharing_update.rs#L8) ignores distribution return data/balances before revoking and replacing shares. Selected current Pump [distribution.rs lines40–55 and77–123](inputs/programs/pump/src/distribution.rs#L40) can return success with native eligibility false; eligible distributions floor each amount and leave dust. Selected AMM [transfer_creator.rs lines55–61](inputs/programs/pump-amm/src/transfer_creator.rs#L55) can return success below its native transfer minimum. Thus the candidate composition does not establish that every old fee unit was paid before changing recipients. Authority is still required; absence of outsider reachability is material. Next prerequisite: establish the exact captured dependency behavior and accrued-fee policy for a permitted historical state, including whether retained dust is intentionally assigned to the new shares. This is not a claim that the captured original loses funds.

| State | Concrete boundary |

Direct lamport changes rely on runtime ownership, writable, conservation and transaction rollback rules. Distinct recipients on social direct transfer are effectively required by simultaneous mutable borrows; source/destination alias in buyback is not similarly rejected. Writable flags are minimum constraints, not rejection of excess caller privileges. No blanket nonalias guarantee is claimed. Generic fee validation, shareholder validation and fresh program-owned creation constrain reachable arithmetic states; deserializers alone do not revalidate those semantic invariants. Clock casts/subtraction and unbounded privileged cooldown settings have been recorded rather than assumed impossible across every runtime.
