# Authentication

How to send an API key, what a key looks like, and how rotation and revocation work.

Every request to `https://api.pump.fun/v1` must carry an API key. Keys are checked at the origin on every request; there is no session, cookie or OAuth flow on this host.

Because there is no signed-in user, **viewer-relative fields are never populated on this host**. Response schemas in the [reference](/reference/) still list them (`viewer.followsYou`, `dmEligible`, `mutuals`, `isFollowing` and the like, which the pump.fun web app fills from the session); on `api.pump.fun` they are always absent, `null` or `false`. Do not build on them.

## Headers

Send the key in one of two headers. Prefer `Authorization: Bearer`; `x-api-key` is an alias for clients that cannot set `Authorization`. The [OpenAPI document](/openapi.public.json) declares a single security scheme, `bearer`, and mentions the alias in that scheme's description, so a client generated from it sends `Authorization: Bearer`.

```http
Authorization: Bearer pf_live_...
```

```http
x-api-key: pf_live_...
```

| Situation                                                | Result                                                                    |
| -------------------------------------------------------- | ------------------------------------------------------------------------- |
| Neither header                                           | `401 API_KEY_REQUIRED`                                                    |
| Both headers, different values                           | Refused as malformed: `401 API_KEY_INVALID`                               |
| `x-api-key` sent more than once                          | Refused as malformed: `401 API_KEY_INVALID`                               |
| `Authorization` with a scheme other than `Bearer`        | Refused as malformed: `401 API_KEY_INVALID`                               |
| Key in a query string                                    | Not read there (and it would end up in logs); treated as no key           |
| Any request header starting with `x-pump-api-`           | Dropped before routing; do not rely on them                               |
| pump.fun session cookie or user JWT sent to the API host | `400 API_CREDENTIAL_NOT_ALLOWED`                                          |
| API key sent to the pump.fun web hosts                   | `400 API_CREDENTIAL_NOT_ALLOWED`; keys work only on `api.pump.fun`        |

Both headers are removed from the request once the key has been read, so nothing behind the key check ever sees it.

## Key shape

```text
pf_live_ + 43 base62 characters + 6 base62 characters   (57 characters total)
```

The 43-character body is 32 random bytes in base62 (`0-9A-Za-z`); the trailing 6 characters are a CRC-32 checksum of the body. Clients do not need to validate the checksum, but secret scanners can match keys on the `pf_live_` prefix and the fixed length. A key that fails the prefix, length, character-set or checksum check is refused before any lookup (`401 API_KEY_INVALID`), and the response does not say which check failed.

The developer console displays a key as its 12-character prefix (`pf_live_` plus four characters) and its last four characters. That display form is safe to put in a support ticket; the full key is not.

## Scopes

Each key carries a set of scopes. A route outside the key's scopes answers `403 API_SCOPE_FORBIDDEN` with `requiredScope` in the body. See [Scopes](/scopes/).

## Rotation

Rotating a key in the [developer console](https://developers.pump.fun) issues a sibling key with the same name, scopes and limits. The old key is not cut off at once: it enters a **grace window** during which both keys work, and is revoked automatically when the window ends.

1. Rotate: choose the grace window (1 hour to 7 days; the default is 24 hours) and copy the new key once.
2. Deploy the new key within the window.
3. Optionally revoke the old key early once nothing uses it. Otherwise it stops working at the end of the window.

During the window the old key shows as `rotating` in the console with the instant it stops being served. A rotating key does not count against your organisation's key limit, so rotation is always possible even when the limit is reached. A key that is already rotating cannot be rotated again (`409 API_KEY_ROTATING`); rotate its successor instead.

## Revocation

Revoking a key takes effect on the next request (`403 API_KEY_REVOKED`). The same applies when an organisation is suspended (`403 API_ORG_SUSPENDED`) or when the pump.fun team changes a key's scopes or limits: the change is visible on the next call.

The API is server-to-server. A request that arrives with a browser `Origin` header from any site other than pump.fun's own is refused with `403` before the key is even read, and the API sends no CORS headers for third-party origins, so a key pasted into front-end code never works. Keys seen in browser traffic are also flagged to the pump.fun team, who may revoke them. The reference page's "Try it" is disabled for the same reason; the snippets it generates are meant to be run from a terminal or a backend.

## If a key leaks

Revoke it in the console immediately, then create a new one. Every call is attributed to a key id (returned to you as the `x-pump-api-key-id` response header), so [support](/status-and-support/) can tell you what a leaked key was used for.

# Errors

The error envelope, every platform error code and what to do about each.

Every refused request, whatever the layer that refused it, answers with one JSON envelope. Branch on `error`; `message` is for humans and may change.

```json
{
"statusCode": 403,
"timestamp": "2026-01-01T00:00:00.000Z",
"path": "/v1/moderation/ban/address/abc",
"error": "API_SCOPE_FORBIDDEN",
"message": "Scope moderation.read required",
"requiredScope": "moderation.read"
}
```

| Field        | Meaning                                                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| `statusCode` | The HTTP status, repeated in the body.                                                                                               |
| `error`      | A stable, machine-readable code. Branch on it.                                                                                       |
| `message`    | Human-readable; may change without notice.                                                                                           |
| `path`       | The request path as the API saw it.                                                                                                  |
| extra fields | `requiredScope` on `API_SCOPE_FORBIDDEN`; `retryAfterMs`, `limit` and `window` on `API_KEY_RATE_LIMITED`.                            |

## Route-level errors

Routes also return their own `400`, `404` and `409` responses, documented per operation in the [API reference](/reference/). For those, `error` is either a registry code listed in the reference (for example `USER_NOT_FOUND`) or a plain HTTP reason phrase (`"Not Found"`). The envelope shape is the same.

One route-level code is worth knowing before you call with an API key:

- `400 API_USER_REQUIRED` on `GET /portfolio-summary` and `GET /portfolio-summary/chart`: these routes serve the signed-in user when `user` is omitted, but an API key is never a session. Send `user=<wallet or username>` on every keyed call; do not retry unchanged.

## Handling checklist

1. `401`: the key is missing or wrong. Fix the header or the key; do not retry unchanged.
2. `403 API_KEY_REVOKED`, `API_ORG_SUSPENDED`, `API_ORG_NOT_APPROVED`: stop calling and check the [developer console](https://developers.pump.fun).
3. `403 API_SCOPE_FORBIDDEN`: request the scope in `requiredScope`.
4. `403 API_REGION_RESTRICTED`: the request came from a region where pump.fun is not available; no key or scope change helps.
5. `429`: wait `Retry-After`, then retry. Check `window` to know whether it was the burst bucket (`burst`), the daily limit (`day`) or one of the per-IP throttles (`auth`, `lookup`); see [Limits and headers](/limits-and-headers/#429-too-many-requests).
6. `503` with no `error` field: wait `Retry-After` (5 seconds), then retry the same request.
7. Anything else: read `error`, log `X-Request-Id`, and quote both in a [support request](/status-and-support/).

# Getting started

Apply for access in the developer console, get approved, create a key and make the first call.

The pump.fun API gives approved organisations read-only access to public social data: profiles, the follow graph, callouts and posts, leaderboards and wallet positions. It is free. Access is by application and approval, keys belong to an organisation, and every call is attributed to the key that made it. Using the API means agreeing to the [Developer API Terms](/terms/).

## Apply and get a key

1. **Open the developer console.** Go to [developers.pump.fun](https://developers.pump.fun) and sign in with your pump.fun account. The sign-in happens on pump.fun and the session carries over.

2. **Apply.** Enter your business name, a business email, your use case, optionally your website, and the scopes you are requesting. Verify the email with the six-digit code we send: it is valid for 10 minutes and five attempts, and you can request a new one after 60 seconds.

3. **Wait for approval.** Applications are reviewed by the pump.fun team. There are no instant keys and no test keys. The decision shows in the console; a rejection carries a note, and a rejected organisation can apply again from the same console. Once the application is approved and the contact email is verified, you can create keys.

4. **Create a key.** Give it a name (`dev`, `prod`, a partner's name) and, optionally, a subset of the default scopes. The full key is shown **once**; store it in a secrets manager. The console keeps only the prefix and the last four characters. An organisation can hold up to five active keys (a key in its [rotation](/authentication/#rotation) grace window does not count), each with its own scopes and limits.

## Make the first call

```sh
curl -sS https://api.pump.fun/v1/users/{id} \
-H "Authorization: Bearer $PUMP_API_KEY"
```

```ts
import { PumpApi } from '@pump-fun/api';

const api = new PumpApi({ apiKey: process.env.PUMP_API_KEY! });
const { data: user, rateLimit } = await api.profiles.getUser({ id: '<wallet or user id>' });
console.log(user.username, rateLimit?.remaining);
```

Replace `{id}` with a user id or a wallet address. A `200` comes back with the profile and the `X-RateLimit-*` headers described in [Limits and headers](/limits-and-headers/). The SDK is documented on its [own page](/sdk/).

## Where the ids come from

Most routes take an id that another route returns: a user id or wallet address from `GET /users/search-v2`, `POST /users/batch` or any profile row; a `calloutId` from `GET /callout/list/{userId}`, `GET /callout/coin/{coin}` or `GET /home-feed/new`.

No public read returns a `postId` except the `/posts` routes themselves. `GET /posts`, `GET /posts/{postId}` and its `/replies`, `/quotes`, `/likers` and `/reposters` all take an id you already hold. Post ids come from the pump.fun app's URLs, `pump.fun/post/<id>`; there is no listing route yet.

## What a new key gets

| Setting               | Default                                             |
| --------------------- | --------------------------------------------------- |
| Scopes                | all read scopes except `moderation.read` (or the subset you pick) |
| Rate                  | 2 requests per second sustained, 120 per 60 s bucket |
| Daily limit           | 50,000 requests per UTC day                         |
| Keys per organisation | 5                                                   |

Defaults start low on purpose. One higher tier is documented: **10 requests per second (600 per 60 s bucket) and 1,000,000 requests per UTC day**. Ask for it by email to [developers@pump.fun](mailto:developers@pump.fun) with the key's prefix and the routes you call (see [Status and support](/status-and-support/)); limits are raised per key, and anything beyond that tier is a partner arrangement.

The API has no CORS for third-party origins. A key that shows up with a browser `Origin` header is flagged to the pump.fun team and revoked. Call the API from your backend and keep the key out of client bundles.

# Limits and headers

Per-second and daily limits, the X-RateLimit headers, Retry-After and the 429 windows.

Limits are set **per key** by the pump.fun team. Every key starts at the defaults below. One higher tier is documented, **10 requests per second (600-request bucket) and 1,000,000 per UTC day**; ask [support](/status-and-support/) for it, or for anything beyond it.

## The two limits

| Limit                 | Default              | How it is measured                                                                                                                                                                      |
| --------------------- | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Rate (`burst` window) | 2 requests per second | A sustained rate with a **60 second bucket**: the bucket holds 60 × the per-second rate, refills continuously, and a request is refused when the bucket is empty. At the default you can send 120 requests at once and then 2 per second. |
| Daily (`day` window)  | 50,000 requests      | A counter per **UTC day** across all routes. Resets at 00:00 UTC.                                                                                                                      |

The two limits count differently:

- The **rate bucket** is debited by every request that passes the key and scope checks, whatever the route then answers. Requests refused for a missing or invalid key, or for a missing scope, do not touch it.
- The **daily counter** counts only requests the API answered successfully (`2xx` or `304`). A slot is reserved before the route runs and handed back when the response is anything else (a `4xx`, a `5xx` or a dropped connection), so refused or failed calls do not spend your daily budget.

The MCP server makes exactly one API request per tool call, so its calls count the same way.

A key whose rate or daily limit has been set to 0 is paused: it answers `429` on every request with `Retry-After: 60` and the message `This key is paused; contact support`, without touching the limiter. To have it unpaused, email [developers@pump.fun](mailto:developers@pump.fun) with the key's prefix (see [Status and support](/status-and-support/)).

## Response headers

Every response to a request whose key was recognised carries these headers, set by the API itself. (A `401` for a missing or unknown key carries `X-Request-Id` only.)

| Header                   | Meaning                                                                                                                                  |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `X-RateLimit-Limit`      | Size of the 60 second bucket (60 × the key's per-second rate).                                                                          |
| `X-RateLimit-Remaining`  | The smaller of the requests left in the bucket and the requests left in today's daily limit. When the daily limit is the tighter one, this number counts down towards it. |
| `X-RateLimit-Reset`      | Unix time in seconds at which the ceiling that `X-RateLimit-Remaining` reports moves: when the bucket is full again, or 00:00 UTC when the daily limit is the tighter one (and on a `day` 429). |
| `Retry-After`            | Seconds to wait. Present on `429` and `503` only.                                                                                        |
| `X-Request-Id`           | Request id generated by the API (a UUID). Quote it in support requests. Any `X-Request-Id` you send is ignored.                          |
| `x-pump-api-key-id`      | Opaque id of the key that made the request (a UUID, never the key itself). Also useful in support requests.                             |
| `Cache-Control`          | Always `no-store`: keyed responses are never cacheable by intermediaries.                                                                |

Deprecated routes add `Deprecation`, `Sunset` and `Link`; see [Versioning and deprecation](/versioning-and-deprecation/).

### Worked example

A key at the default rate has just made its second call of the minute. The bucket holds 60, 58 are left, and it will be full again at the Unix second in `X-RateLimit-Reset`:

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Cache-Control: no-store
X-RateLimit-Limit: 60
X-RateLimit-Remaining: 58
X-RateLimit-Reset: 1767225660
X-Request-Id: 7d1f0a2e-5b8c-4b1e-9a7f-2c3d4e5f6a7b
x-pump-api-key-id: 3f9c2b1a-4d5e-4f60-8a7b-9c0d1e2f3a4b
```

Sixty more calls in the same second empty the bucket; the sixty-first is refused and tells you how long to wait:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 1
Cache-Control: no-store
X-RateLimit-Limit: 60
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1767225661
```

## 429 Too Many Requests

A refused request answers `429` with `Retry-After` and this body:

```json
{
"statusCode": 429,
"timestamp": "2026-01-01T00:00:00.000Z",
"path": "/v1/users/123",
"error": "API_KEY_RATE_LIMITED",
"message": "Rate limit of 60 requests per minute exceeded",
"retryAfterMs": 1000,
"limit": 60,
"window": "burst"
}
```

`window` tells you which limit was hit:

| `window` | Meaning                                                                                                     | What to do                                                            |
| -------- | ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `burst`  | The 60 second bucket is empty.                                                                              | Wait `retryAfterMs` (usually under a second at the default rate).     |
| `day`    | The UTC-day counter reached the daily limit. The message reads `Daily limit of 50000 requests reached; resets at 00:00 UTC` and `X-RateLimit-Reset` points at that midnight. | Wait until 00:00 UTC (`Retry-After` says how long), or ask for a higher daily limit. |
| `auth`   | Too many **failed** keys from your IP address (60 per 10 minutes). Only unknown, malformed, revoked, suspended or not-yet-approved keys count. | Fix the key you are sending; valid keys are never throttled this way. |
| `lookup` | Too many **uncached** key lookups from your IP address (600 per 10 minutes). A recognised key is cached for five minutes, so steady traffic with a few keys never reaches this; a flood of distinct keys from one address does. | Reuse your keys instead of sending many different ones from one address. |

## 503 Service Unavailable

If the API cannot check a key or its limits because a backing store is unavailable, keyed requests **fail closed** with `503` and `Retry-After: 5`. The body is a fixed envelope with no `error` field:

```json
{
"statusCode": 503,
"timestamp": "2026-01-01T00:00:00.000Z",
"path": "/v1/users/123",
"message": "API platform temporarily unavailable; retry after 5s",
"retryAfterSeconds": 5
}
```

Retry after the interval with the same request; do not retry in a tight loop.

## Client guidance

- Read `X-RateLimit-Remaining` and slow down before you hit 0 instead of reacting to `429`s.
- Honour `Retry-After` on both `429` and `503`.
- Use one key per deployment (`dev`, `prod`) so one noisy environment does not consume another's budget.
- Batch where a route supports it (for example `POST /users/batch` instead of many `GET /users/{id}` calls): one request is one unit regardless of batch size.

# MCP server

Connect Claude Code, Claude Desktop or Cursor to pump.fun social data with your API key.

pump.fun runs a hosted [Model Context Protocol](https://modelcontextprotocol.io) server at **`https://mcp.pump.fun/mcp`** (Streamable HTTP). It exposes the same read-only data as the API as {mcp.tools.length} tools, authenticated with the same `pf_live_` key. Each tool call is exactly one API request and counts against your key's [limits](/limits-and-headers/) like any other call.

The server is stateless: every request is a `POST /mcp` with a JSON-RPC body and a JSON response. There are no sessions and no server-sent event streams; `GET /mcp` answers `405`.

## Connect

Pass your key as a bearer header. The MCP server only accepts `Authorization: Bearer pf_live_...`: the `x-api-key` alias is refused (`400`), and so is any request that carries a browser `Origin` header (`403`), including browser-hosted MCP inspectors.

```sh
claude mcp add --transport http pump https://mcp.pump.fun/mcp \
--header "Authorization: Bearer pf_live_..."
```

Add to `claude_desktop_config.json` (Settings → Developer → Edit Config):

```json
{
"mcpServers": {
"pump": {
"url": "https://mcp.pump.fun/mcp",
"headers": { "Authorization": "Bearer pf_live_..." }
}
}
}
```

Add to `.cursor/mcp.json` in your project (or the global one):

```json
{
"mcpServers": {
"pump": {
"url": "https://mcp.pump.fun/mcp",
"headers": { "Authorization": "Bearer pf_live_..." }
}
}
}
```

Clients that cannot speak HTTP directly can bridge through `mcp-remote`:

```json
{
"mcpServers": {
"pump": {
"command": "npx",
"args": [
"-y", "mcp-remote", "https://mcp.pump.fun/mcp",
"--header", "Authorization: Bearer ${PUMP_API_KEY}"
]
}
}
}
```

The MCP server only checks that the bearer has the shape of a key (`pf_live_` plus 49 characters; anything else is a `401` before MCP starts). Validity, scopes and limits are checked by the API when a tool runs, so a well-formed but wrong key connects fine and fails on the first tool call with `invalid_key`.

## Tool results

Every successful result has a `content[0].text` that starts with one fixed line explaining the untrusted wrapper, followed by the JSON, and a `structuredContent` with `data` and `meta`:

| `meta` key                    | Contents                                                                                                   |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `fun.pump/untrustedFields`    | Paths of user-generated strings; each is `{ "untrusted": true, "text": "..." }` in place.                  |
| `fun.pump/strippedFields`     | Viewer-relative fields removed before shaping.                                                             |
| `fun.pump/upstream`           | The API's `X-Request-Id`, `X-RateLimit-*`, `Retry-After` and, on a deprecated route, `Sunset` / `Deprecation`. Quote the request id in support requests. |
| `fun.pump/page`               | The page size actually sent, and `clampedFrom` when you asked for more.                                    |

## Tool errors

Tool errors (`isError: true`) carry `structuredContent.error`, derived from the API's [error envelope](/errors/). Every upstream failure also carries `status` (the API's HTTP status), `code` (the API's error code, when it sent one) and `requestId`.

| Tool error             | API code                                                                                        |
| ---------------------- | ----------------------------------------------------------------------------------------------- |
| `invalid_key`          | `API_KEY_REQUIRED`, `API_KEY_INVALID`                                                           |
| `key_revoked`          | `API_KEY_REVOKED`, `API_ORG_SUSPENDED`                                                          |
| `key_not_approved`     | `API_ORG_NOT_APPROVED`                                                                          |
| `insufficient_scope`   | `API_SCOPE_FORBIDDEN` (carries `requiredScope`)                                                 |
| `rate_limited`         | `API_KEY_RATE_LIMITED` (carries `retryAfterSeconds` and `rateLimit.limit/remaining/reset/window`) |
| `upstream_unavailable` | any `503`                                                                                       |
| `upstream_error`       | anything else; `status: 404` is "no such record", `status: 400` is "the API rejected the input" |

| `disabled`             | the tool is switched off on the server (no API code)                                            |

## Untrusted content

Callout text, replies, bios, usernames and group names are written by pump.fun users. The MCP server marks these fields as **untrusted** in every tool result (an explicit `untrusted: true` wrapper on the text, with the paths listed in `meta["fun.pump/untrustedFields"]`) so that an agent does not follow instructions hidden in them, and it never turns URLs found in user content into links or instructions. Viewer-relative fields (`isFollowing`, `viewerFollows`, mute state) are stripped: the server has no viewer.

## Later: OAuth

The server has an RFC 9728 protected-resource metadata endpoint at `/.well-known/oauth-protected-resource` so an OAuth 2.1 flow can be added without changing the endpoint. Today the metadata is not advertised and the bearer key is the only credential.

# Scopes

The six scope families, how many routes each unlocks, and the full route list per scope.

A key carries a set of scopes. Each public route belongs to exactly one scope, and a call to a route outside the key's scopes is refused with `403 API_SCOPE_FORBIDDEN` and `requiredScope` naming the scope you need.

New keys receive every scope **except** `moderation.read`; when creating a key you may also pick a smaller subset of that default grant. Only the pump.fun team can add `moderation.read` or change a key's scopes afterwards; ask [support](/status-and-support/).

## Notes

- `moderation.read` is the public ban oracle (`GET /moderation/ban/address/{address}`). It answers whether a wallet address is banned on pump.fun and nothing else. It is outside every default grant because it is an oracle: request it only if your product needs it.
- The `/posts` routes (`content.read`, with `/likers` and `/reposters` under `graph.read`) take a post id you already hold: no public route returns a `postId`. Post ids come from the pump.fun app's URLs, `pump.fun/post/<id>`; there is no listing route yet. See [Getting started](/getting-started/#where-the-ids-come-from).
- Scopes are read-only by construction. There is no write, trading or on-behalf-of scope and none is planned.
- Market data (coin prices, trades, candles) is **not** part of this API today.

# TypeScript SDK

The @pump-fun/api client, typed from the public OpenAPI document, with zero runtime dependencies.

`@pump-fun/api` is a typed TypeScript client for `https://api.pump.fun/v1`. It has no runtime dependencies, uses the global `fetch` (Node 20 or newer), ships ESM and CommonJS, and types every route from the same [OpenAPI document](/openapi.public.json) this site serves. It is MIT-licensed.

The constructor refuses to run in a browser. Keep the key in a secrets manager or an environment variable on your server; a key that reaches a browser is [revoked](/authentication/#revocation).

## Install

```sh
pnpm add @pump-fun/api
# or: npm install @pump-fun/api
```

The package is published to the public npm registry with the API's general availability. Until then the install command above will not resolve.

## First call

```ts

const api = new PumpApi({ apiKey: process.env.PUMP_API_KEY! });

const { data: user, rateLimit } = await api.profiles.getUser({ id: '<wallet or user id>' });
console.log(user.username, rateLimit?.remaining);
```

Every route method takes one argument: path parameters at the top level, `query` for query parameters and `body` for JSON bodies. A second, optional argument carries per-call options (`signal`, `timeoutMs`, `maxRetries`, `headers`). The result is an object with these fields:

| Field        | Type                       | Meaning                                                                    |
| ------------ | -------------------------- | -------------------------------------------------------------------------- |
| `data`       | typed per route            | The parsed response body.                                                  |
| `status`     | `number`                   | HTTP status code.                                                          |
| `headers`    | `Headers`                  | The raw response headers.                                                  |
| `requestId`  | `string \| null`           | `X-Request-Id`; quote it in support requests.                              |
| `apiKeyId`   | `string \| null`           | `x-pump-api-key-id`, the opaque id of the key that made the call.          |
| `rateLimit`  | `{ limit, remaining, reset, resetAt }` | Parsed from the `X-RateLimit-*` headers, or `null` when absent. See [Limits](/limits-and-headers/). |
| `deprecation` | `{ announced, sunset, successor, docs, raw }` | Parsed from the `Deprecation`, `Sunset` and `Link` headers when the route is deprecated; otherwise `null`. |

## Options

```ts
const api = new PumpApi({
apiKey: process.env.PUMP_API_KEY!, // required, pf_live_...
baseUrl: 'https://api.pump.fun/v1', // the default
maxRetries: 2, // retries after 429 / 5xx / connection failures; 0 disables
maxRetryDelayMs: 30_000, // a longer Retry-After throws instead of waiting
timeoutMs: 30_000, // per request
headers: {}, // extra headers; Authorization, User-Agent and x-pump-sdk are managed
warnOnDeprecation: true, // one console.warn per deprecated route; false to silence
});
```

Every request carries `Authorization: Bearer <key>`, `Accept: application/json`, `User-Agent: @pump-fun/api/<version>` and `x-pump-sdk: @pump-fun/api/<version>`. Redirects are refused so the key never follows a `Location` to another host, and the `request()` escape hatch accepts only paths under `baseUrl`, never an absolute URL.

## Route families

One namespace per [scope](/scopes/). Method names follow the OpenAPI `operationId`.

| Namespace          | Scope               | Routes | Examples                                                          |
| ------------------ | ------------------- | ------ | ----------------------------------------------------------------- |
| `api.profiles`     | `profiles.read`     | 13     | `getUser`, `searchUsers`, `getUsersBatch`, `resolveIdentifiers`   |
| `api.graph`        | `graph.read`        | 17     | `getFollowers`, `getFollowing`, `checkFollows`, `getGroupMembers` |
| `api.content`      | `content.read`      | 18     | `getCallout`, `listUserCallouts`, `getRecentCallouts`, `listPosts` |
| `api.leaderboards` | `leaderboards.read` | 11     | `getPnlLeaderboard`, `listCompetitions`, `getCreatorPayoutsLeaderboard` |
| `api.positions`    | `positions.read`    | 7      | `getUserPositions`, `getUserTrades`, `getCoinHolderPositions`     |

`ROUTES` exports the full table (method, path, operationId, scope) and `listRoutes()` flattens it.

```ts
// graph.read: who follows a user, paginated with limit/offset
const { data: followers } = await api.graph.getFollowers({
userId: user.address,
query: { limit: 50, offset: 0 },
});

// leaderboards.read: the weekly PnL leaderboard
const { data: board } = await api.leaderboards.getPnlLeaderboard({ query: { period: 'weekly', limit: 25 } });

// positions.read: a wallet's positions in the given coins
const { data: positions } = await api.positions.getUserPositions({
userId: user.address,
query: { mints: ['<coin mint>'] },
});
```

## Errors and retries

On `429`, `5xx` and connection failures the client retries up to `maxRetries` times (default 2), waiting for `Retry-After` when the response carries it, else the body's `retryAfterMs`, else an exponential backoff from 500 ms with jitter. If a single wait would exceed `maxRetryDelayMs` (default 30 s) the error is thrown at once so you can schedule the retry yourself. No other `4xx` is retried, and timeouts are not retried.

Once retries are exhausted, every non-2xx response throws a `PumpApiError`:

| Field                              | Meaning                                                                                                   |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `status`                           | HTTP status; `0` for timeouts and connection failures.                                                    |
| `code`                             | `error` from the [envelope](/errors/), a route code such as `CALLOUT_NOT_FOUND`, or one of the SDK's own: `HTTP_ERROR`, `TIMEOUT`, `NETWORK_ERROR`. |
| `method`, `path`                   | The request that failed.                                                                                  |
| `requestId`, `apiKeyId`            | The `X-Request-Id` and `x-pump-api-key-id` headers; quote the first in support requests.                  |
| `retryAfterMs`, `retryAfter`       | From `Retry-After` (seconds or HTTP-date) or the body's `retryAfterMs`; set on `429` and `503`.           |
| `rateLimit`                        | Parsed `X-RateLimit-*` headers.                                                                           |
| `requiredScope`, `window`, `limit` | Details on `API_SCOPE_FORBIDDEN` and `API_KEY_RATE_LIMITED`.                                              |
| `body`, `envelope`, `headers`      | The raw body, the parsed envelope when the body was one, and the response headers.                        |
| `isRetryable`, `isAuthError`       | Convenience flags.                                                                                        |

`PumpApiTimeoutError` (`code: 'TIMEOUT'`) and `PumpApiNetworkError` (`code: 'NETWORK_ERROR'`) extend `PumpApiError`. A caller `signal` abort propagates as an `AbortError`.

```ts
const address = '<wallet address>';

try {
await api.moderation.checkAddressBanned({ address });
} catch (err) {
if (err instanceof PumpApiError && err.code === 'API_SCOPE_FORBIDDEN') {
// request moderation.read from developers@pump.fun
} else {
throw err;
}
}
```

## Deprecations

A deprecated route answers with `Deprecation`, `Sunset` and `Link` headers. The client parses them into `result.deprecation` (`announced` and `sunset` as dates, `successor` from the `Link` header's `rel="successor-version"`, `docs` from a `rel="deprecation"` link if the API ever sends one, and the `raw` header values) and emits one `console.warn` per route per client instance. Pass `warnOnDeprecation: false` to the constructor to silence the warning and act on `result.deprecation` yourself, for example by counting it in your metrics. Routes are deprecated with at least 90 days' notice; see [Versioning and deprecation](/versioning-and-deprecation/).

## Key format helper

```ts

isValidKeyFormat('pf_live_...'); // prefix + 43 base62 body + 6 base62 CRC-32 checksum = 57 chars
parseKey('pf_live_...'); // { ok: true, body, checksum, displayPrefix, last4 } | { ok: false, reason }
```

The constructor itself checks only the prefix, length and character set; use `isValidKeyFormat` when you want the checksum verified, for example when reading the key from configuration.

# Status and support

How availability is communicated and how to reach the pump.fun team about the API.

## Availability

- There is no contractual SLA for the API, and no SLA on support replies.
- There is no public status page for the API yet. When one exists it will be linked from this page.
- When the API cannot verify keys or limits it fails closed with `503` and `Retry-After: 5` (see [Limits and headers](/limits-and-headers/#503-service-unavailable)); treat a run of those as an incident on our side and retry after the interval.

## Support

Support for the developer API is by email: write to [developers@pump.fun](mailto:developers@pump.fun). The team reads the mailbox on business days and answers in order; there is no SLA on a reply. Decisions on applications, and the note that comes with a rejection, show in the [developer console](https://developers.pump.fun), so check there first.

The mailbox is for:

- the status of an application,
- raising a key's rate or daily limit,
- adding a scope to a key or an organisation,
- an incident: errors, timeouts or wrong data from the API,
- questions about a deprecation or a sunset date.

In every request include:

- your **organisation name** as the developer console shows it,
- the key's **12-character prefix** (`pf_live_` plus four characters), as the console shows it. **Never send the full key.** If a full key has reached anyone, revoke it in the console first.
- the `X-Request-Id` response header of a failing call (and `x-pump-api-key-id` if you have it),
- the **time in UTC** and the **route** of the call,
- what you expected and the response body you got.

## Requests we handle

| Request                                     | What to send                                                                                                   |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Status of an application                    | organisation name; the decision itself shows in the [developer console](https://developers.pump.fun)           |
| Raise rate or daily limits                  | key prefix, routes you call, expected volume                                                                   |
| Add a scope (for example `moderation.read`) | key prefix, the product need                                                                                   |
| Report an incident or a bug in the data     | request id, route, time (UTC), what you expected                                                               |
| Ask about a deprecation                     | the route and the `Sunset` date from its headers                                                               |
| Report a leaked key                         | revoke it first in the [developer console](https://developers.pump.fun), then tell us the prefix, never the key |

## Changes and deprecations

Deprecations are announced with the headers described in [Versioning and deprecation](/versioning-and-deprecation/) and in the OpenAPI document (`deprecated: true` on the operation), at least 90 days before a route is removed. Questions about a deprecation go to [developers@pump.fun](mailto:developers@pump.fun).

# Versioning and deprecation

The /v1 contract, what counts as a breaking change, and the 90-day deprecation headers.

## The `/v1` contract

The base URL is `https://api.pump.fun/v1`. The version lives in the path and will stay `v1` for as long as the routes below keep their request and response shapes. The OpenAPI document at [`/openapi.public.json`](/openapi.public.json) is the contract. (Its `info.version` is the version of the contract release the document was published under, the same number as the `public-api-spec-v<version>` release that carries it, not the API version; the API version is the path prefix.)

### Changes that ship without notice (additive)

- New routes, new optional query parameters, new optional request-body fields.
- New fields in responses. **Ignore fields you do not know**; do not fail on them.
- New values in open sets (for example a new `kind` on a profile) where the reference marks the set as open.
- New error codes on existing status codes.

### Changes that require a deprecation period (breaking)

- Removing a route, a parameter or a response field.
- Changing a field's type or making an optional field required.
- Narrowing or renaming values in a closed enum.

A breaking change to a route is shipped as a **new route** (or a new parameter form) alongside the old one; the old one is then deprecated.

## Deprecation: 90 days minimum

A deprecated route keeps working for **at least 90 days** after the announcement. During that time it answers with up to three extra headers, on every response including errors:

| Header | Example | Meaning |
| --- | --- | --- |
| `Deprecation` | `Deprecation: @1775001600` | When the deprecation was announced: `@` followed by the Unix time in seconds of midnight UTC on that day ([RFC 9745](https://www.rfc-editor.org/rfc/rfc9745)). |
| `Sunset` | `Sunset: Tue, 30 Jun 2026 00:00:00 GMT` | The earliest date after which the route may be removed, as an HTTP-date ([RFC 8594](https://www.rfc-editor.org/rfc/rfc8594)). Always 90 or more days after `Deprecation`. |
| `Link` | `Link: </v1/users/123/overview>; rel="successor-version"` | The replacement route, when there is one ([RFC 8288](https://www.rfc-editor.org/rfc/rfc8288)). Absent when the route has no successor. The target is a path on the API origin, `/v1` prefix included, with the path parameters of your request filled in; a successor on another host is given as an absolute URL. |

The OpenAPI document reflects it: the operation is marked `deprecated: true`, carries `x-deprecation-since` and `x-sunset` (ISO dates) and, when there is a replacement, `x-successor` (the replacement route as `METHOD /path`, or an absolute URL), and its success responses list the `Deprecation`, `Sunset` and `Link` headers. Watch for `deprecated` in the document or for the `Deprecation` header in your responses: both are machine-readable and change before anything stops working.

No route is deprecated today.

## How to stay informed

- The OpenAPI document is refreshed whenever the API changes; diff it on a schedule if you generate code from it.
- Questions about a deprecation go to [developers@pump.fun](mailto:developers@pump.fun) (see [Status and support](/status-and-support/)).
- Metrics on the API side show which keys still call a deprecated route; if yours does, expect to be contacted before the sunset date.
