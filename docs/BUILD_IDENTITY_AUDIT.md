## Why the v1.43 conclusion was wrong

The restored recipe report first called v1.44 proven, then called v1.43 proven because `.text` sizes were closer. Neither inference establishes the historical recipe. Fresh independent parsing finds all three proposed v1.43 candidates have ELF `(e_machine,e_flags)=(247,0)`, while all four target captures have `(263,0)`. The mismatch begins at byte18, before layout offsets. The official v1.43 backend selects `(247,0)` for generic and `(263,32)` for `sbfv2`; the official v1.44 backend selects `(263,0)` for generic. Five fresh llc object probes reproduce this transition without using any program or captured executable as compiler input.

The Fees target's complete 352-byte multiplication helper is raw-identical to the retained v1.44 body. v1.43 differs at instruction offsets160 and216. The prior controlled experiment also finds v1.44 raw-exact 1,056-byte `core::fmt::write`, with negative full-body results for v1.45/v1.46. Panic helpers that match several versions are nondiscriminating controls. These observations favor the stock v1.44 distribution for Fees; they do not rule out all custom sysroots, mixed compiler/linker phases or unknown profiles. Fees results are not independent full compiler proofs for Pump/AMM. The formerly missing v1.46.1 measurement is now [published separately](../repro/identity-audit/2026-10-25/compiler-v1461/REPORT.md): one offline frozen16 build preserves11 source/lock inputs and the53-file SDK map, with an explicitly adapted `sbpf-solana-solana` generic-v0 target because the release no longer ships the legacy target. Full fmt/multiply/Unicode helpers remain negative, matching v1.46's weaker results. This is measured stock-recipe evidence, not exclusion of unknown custom profiles or pipelines.

For Mayhem, `raw_vec/mod.rs` and `hashbrown-0.15.4` identify source families, not one compiler distribution. An older compiler failing to build the reconstructed lockfile only constrains that lockfile. A newer compiler failing with an older build driver's target name is a setup failure, not exclusion of the original compiler. The v1.52/v1.53/v1.54 family needs compatible driver/target combinations and complete target-helper/call/data comparisons.

The `.text` ratios previously labelled “99.9%/99%/86% source complete” are only lengths. Unrelated instruction bodies may have equal lengths; generic specialization, inlining, macro-generated code, dependency implementation and code ordering can change size without changing handler coverage. A net section deficit is not a count of undecompiled instructions or missing source bytes. Lost original source is an uncertainty, not an impossibility proof.

## SDK and dependency closure still missing

SDK testing needs a revision-pinned action→instruction→account→CPI matrix, with each action's actual success and rejection domain. Three seeded global accounts do not establish full SDK compatibility. Pump, AMM and Fees official IDLs are retained snapshots; compare the chosen client SDK revision's discriminators, serialization, optional argument shapes, signer/writable flags, PDA seeds, token extensions and program IDs against that exact deployment snapshot. Mayhem has no retained official IDL, so document the inferred interface and its limits.

The restored localnet script hardcoded older candidates, omitted Donation Relay and deleted a caller-selected ledger. This audit fixes those defects: the launcher resolves status artifacts, verifies owning build/capture hashes, includes all five dependencies, binds localhost and refuses existing ledgers or symlinks. Four fixture tests exercise the actual launcher with a mocked validator. After the current Fees pointer repair, its dry run validates all nine program hashes and three seed records without creating a ledger; no validator startup is claimed. Loading all nine programs still does not create the per-flow mints, pools, volume schedules, sharing configs, relayer/whitelist state and legitimate signer paths each SDK action requires. A successful validator startup is not an SDK acceptance result.

Two dependencies have exact retained source-build proofs; that does not identify every in-process Rust crate. The contract build closure must separately pin the complete Cargo unit/feature graph, proc-macro/Anchor expansion, patches, vendored sources, enabled cfgs and archive checksums. Embedded crate paths are version witnesses for compiled files, not proof of every unreferenced package or all feature selections.

## Build recipe evidence required before identity can close

1. Exact source tree, paths, generated IDLs/macros, lockfile, enabled features and cfgs; distinguish reconstructed compatibility pins from target version evidence.
2. Rust fork commit, LLVM fork commit, Cargo version, bootstrap configuration, sysroot rlib/object bytes and host distribution. `rustc --version` alone is insufficient.
3. Build driver, target triple/CPU/features/ABI, linker and linker script, SDK installer/env/strip scripts and actual postprocessing executable. Existing Darwin recipes use v1.44 compilation and separately attributed v1.52 stripping; the official Linux SDK defaults another strip phase.
4. Safe allowlisted build-environment/process trace, including actual `RUSTFLAGS`, encoded flags, compiler wrappers, linker/archiver selection, Cargo configuration and profile overrides. Do not publish arbitrary environment or credentials.
5. Complete original/candidate function boundaries, raw bytes, relocation patterns, direct/indirect call targets and referenced data extents. Match recursive closure; keep unmatched and ambiguous rows.
6. Two independent clean source builds under the same complete recipe, followed by a full payload comparison. A successful candidate must have the exact target SHA, expected loader allocation, complete source provenance and no copied target instructions as build inputs.
